## What works today

The dream flow, Dream log and Dream entry are built and covered by tests, but **mostly not yet verified on a physical device** (see Gaps):

1. **Capture** (`CaptureScreen`): idle view ("What happened in my dream?", tips, tap-to-talk button, "Write instead", "No dream"). Recording uses `expo-audio` while `expo-speech-recognition` shows **live on-device text** (a few of the newest words, older ones fading). A quiet status row shows "Listening · m:ss" or "Paused · m:ss" (the empty-transcript body reads "Listening..." or "Paused"), above a live waveform driven by the mic level. Pause/resume: the recorder pauses or resumes first, recognition stops while paused and a new session starts on resume; if the OS restarts the recorder while the UI says paused, a debounced check pauses it again (up to 3 times, then the screen follows the recorder). Save dream stops both and moves on. A quiet **"Type instead"** control sits on the listening screen (recording or paused; disabled while saving or stopping). It asks "Type instead?" / "Your recording will be deleted. The text so far is kept." (Keep recording / Type instead). On confirm it stops live text and the recorder, deletes that recording's cache file, and opens Read it back with the live text so far as a written dream with no audio (session origin `write`, transcript prefilled, text box focused; `startWriting(transcript = '')`). If stopping fails, nothing is deleted and the usual "Could not finish recording" alert shows.
2. **Read it back** (`ReadItBackScreen`): the transcript in an editable text box, the original recording playable below it (the card is unmounted while the keyboard is up, so playback stops and its position resets when the keyboard opens; accepted; while the keyboard is up a "Hide keyboard" text button above Continue dismisses it), Continue (enabled with non-blank text or a recording). The back arrow goes to a "Discard this dream?" confirmation for a new dream with something at stake; back from a reopened draft returns to the Dream log (a path that cannot happen today: a draft's Read it back always comes from Review's Edit, which returns to Review); back after Edit on Review returns to Review.
3. **Review** (`ReviewScreen`): title (required to finish), a 3-line transcript preview with Edit, "How did it feel?" (optional; an emotion input like the tag input, with quick-pick chips from emotion words used before), tags (optional; laid out like the emotion section: **Tag input** (`TagInput`) on top with the placeholder "Add a tag...", added tags as chips directly under it (tap a chip or its ✕ to remove), then the "+ tag" suggestion chips in a row below, from tags used before, with accessibility labels like "Add tag water"; the emotion suggestion chips are labeled the same way, "Add emotion calm"). Enter on the tag and emotion inputs keeps the keyboard open (`returnKeyType="done"`, `submitBehavior="submit"`). **Done** needs a title and saves a finished dream; **Finish later** saves a draft (a brand-new dream with nothing at all to keep, meaning no audio, text, title, emotion or tags, is not saved: the app just goes to the Dream log). Back goes to Read it back (new dream) or saves the reopened draft's edits and returns to the Dream log. When Review was opened with Edit on a finished dream (origin `edit`): "Finish later" is hidden; **Done** needs a title, saves the dream as finished and returns to that dream's entry; with no changes Done skips the write and returns to the entry; back with unsaved edits asks "Discard changes?" (Keep editing / Discard), and without edits it just returns. An edit never calls `save('draft')` and never discards persisted audio. While a save is in flight, back (arrow and Android hardware back) does nothing, and Done, Finish later, the transcript card and the title field, the emotion input (chips too) and the tag controls are locked.
   - **Emotion input** (`EmotionInput`): a single-line input with the placeholder "Add an emotion...". Enter (or a comma or semicolon) creates the emotion: trimmed, lowercased, inner spaces collapsed, cut to 40 characters, case-insensitive duplicates ignored; text with commas or semicolons creates several. Added emotions show as amber chips under the input (capitalized for display only; tap a chip to remove it). Emotions used before appear as "+ calm" suggestion chips (at most 8, not already added, filtered by the typed text); tapping one adds it. An emotion typed but not yet submitted is kept like a pending tag (session `emotionDraft`): it survives Edit text and back, counts as an edit, and is saved on Done or Finish later (`withPendingEmotion`). Storage is unchanged: `Dream.emotion` stays one optional lowercase string joined with ", "; older free-text emotions still show split on commas and semicolons (and are rewritten in the joined form only when the user changes the emotions on Review).
4. **Dream log** (`DreamLogScreen`): header "Dreams" with a search icon. Month sections (month in capitals, the year added when not the current year, "EARLIER" for a missing or invalid date). Tag chips: "All · N" and "tag · count" (the 20 most-used tags, selected tags always shown), multi-select; a dream must have ALL selected tags. Search (the icon replaces the title with a field and Cancel; the field has a clear (×) button once something is typed, and the "New dream" button is hidden while search is open) matches every typed word against title, transcript, emotion and tags (lowercased, accents stripped where the engine supports it; local text matching only) and combines with the tag filter. Rows: weekday and day, title (a short date when a finished dream has no title, "Untitled dream" when the date is missing or invalid), a 2-line transcript preview, emotion and tag chips (at most 4 chips in all, of which at most 2 are emotions, plus a "+N" overflow chip); no play button. **Rows, drafts included, swipe left to reveal a red "Delete"** (legacy `Swipeable` from `react-native-gesture-handler`; the revealed action is a 44pt button); tapping it shows the same "Delete this dream?" Keep / Delete confirmation as the entry. Every row also exposes an accessibility custom action "Delete" (swiping is unreachable with VoiceOver/TalkBack). A draft's delete confirmation and storage path are the same as a finished dream's (`deleteDream` removes its audio too). One row is open at a time (it closes on scroll and when another row or a dream is opened). Notes-style in-flight: only the row being deleted is dimmed and untappable, and swiping is disabled on all rows until it finishes; browsing, search, tag filters, opening other dreams and Android back stay free. A delete from the log does not navigate. Drafts appear inline by date as an outlined card (no chevron): title "Untitled dream" (or the title), with " · m:ss" when it has audio, and the sub-line "Draft · <date>" (short date such as "Oct 4", with the year when not the current year; "Draft" in red, the date in the muted color; just "Draft" when the date is invalid); its accessibility label is "Draft: <title>. <long date>. Tap to finish"; tapping opens Review. The search field has a minimum height, line height and vertical padding so its placeholder is not clipped, and the clear (×) button is 42 high so it no longer makes the search pill grow. A "New dream" button (mic icon) opens capture. Empty ("No dreams yet."), no-results (with Clear) and unreadable-index states. The filter, search and scroll offset live in `useLogView` in `App.tsx`; the offset is restored once when the log is shown again.
5. **Dream entry** (`DreamDetailScreen`, finished dreams only): back and a top-right **"..." More options menu** (`OverflowMenu`, an in-screen overlay, not a `Modal`; closes on backdrop tap, on picking an item, and on Android back) holding Edit and a red Delete; a centered header date ("Dream · Sunday, October 4", "Life · …" for Life, the journal name alone with no date; same format as Read it back and Review, no time); the title (an untitled Dream still shows its short date as the heading, which repeats the header; an untitled Life entry has no heading); all emotion and tag chips; a compact audio player when the dream has audio; the transcript in paragraphs, or "No text yet". Edit opens Review for that dream (see Review above). Delete is the second menu item (finished dreams only; the menu item is absent when the screen gets no `onDelete`; disabled while this delete runs and while another delete is in flight, `deleteBlocked`). It opens a native confirmation (shared copy in `src/utils/confirmDelete.ts`), "Delete this dream?" / "The recording and text will be permanently deleted. This can't be undone." (no audio: "The text will be permanently deleted. This can't be undone."), with Keep and Delete. On Delete the player is unmounted (releasing the audio) and `App` calls `useDreamLibrary.remove(id)`; while it runs the menu's Delete is disabled and back (arrow and Android hardware back) and Edit are ignored, like back during a save. On success the app goes to the Dream log (only for a delete started on the entry), keeping its filter, search and scroll. On failure an alert "Could not delete dream" shows and the entry stays, with a retry possible: "Your saved dreams could not be read. Nothing was deleted." (unreadable index), "A saved copy of your dreams is damaged, so this dream was not deleted. Nothing was changed." (a safety copy blocks the delete; user-approved wording, 2026-10-10) or "Please try again." (anything else). The screen never touches storage and shows no alerts of its own on failure. Not built: "Also tagged" and "See all".
6. **"Write instead"** opens Read it back with an empty, focused text box and creates a dream with no audio (the microphone is never touched). Read it back focuses its text box for every `write`-origin session, so "Type instead" with some text also opens focused (a recording that is saved normally does not autofocus). **"No dream"** exists on the launch Dream capture only; it saves today's date as the skip marker and opens Today (see Today below).

8. **Android hardware back**: the entry goes to where it was opened (Today, its log, or Search); the log with search open closes search; with search closed, Back on the log goes to the Journals home, whose back goes to Today, where Android back exits the app (as the launch Dream capture does; this replaces the 2026-10-06 rule that the log returned to capture and the earlier rule that the Journals home exited); Read it back and Review mirror the on-screen back arrows. Back is blocked while a save is in flight, which covers an edit too, and while a delete started from the entry is in flight (a delete from the Dream log does not block back). On Android back, an open "..." menu closes first.

10. **Today, Settings and the launch rule** (user decisions 2026-10-10; Part 2 of the journals plan).

- **Today** (`TodayScreen`): header with a book icon top left (`BookIcon`, label "Open Journals"), the title "Today" and the date, and a gear top right (`GearIcon`, "Open Settings"; both in `src/components/TodayIcons.tsx`). The list is `entriesToday` (`src/utils/today.ts`): entries whose `createdAt` falls on today's local date (`localDateKey`, never `toISOString`), from every known journal, drafts included, newest first, flat; a record with a missing or invalid `createdAt` never shows. Each row is a `SwipeEntryRow` (the swipe-to-delete row extracted from the Dream log, with a journal label "Dreams" or "Life" and per-journal delete wording). A quiet "No dream today" line shows when the skip marker is today and no Dream entry or draft exists today; empty states "Nothing here yet today." / "Nothing else yet today." (with the skip line), and the unreadable-index message. Bottom buttons "New dream" (a 150pt `FAB_CLEARANCE` list padding keeps rows clear of them) and "New Life entry". No search. All wording is `TODAY_COPY`.
- **Launch rule** (`launchScreen` in `today.ts`, run once in `App.tsx`): `screen` starts `null` (a blank background view) until the library, the No dream marker and the settings have all loaded; then `dayStatus` (a finished Dream created today; the skip date equals today; drafts and Life entries do not count) and the toggle pick Dream capture (auto-open on and nothing done) or Today. A 1000 ms cap (`LAUNCH_CAP_MS`) opens Dream capture if the data is not ready; late data then never moves the user (`launchResolved`). The launch capture (`captureLaunch`) has no back arrow, Android back exits, and it alone offers "No dream".
- **Transitions**: saving, "No dream" and "Finish later" from the launch capture go to Today. `flowReturn` (`'today' | 'log'`) says where a capture, or a draft opened for Read it back and Review, returns after a save or on back: captures from Today return to Today, captures from a log return to that log. Dream capture from the Dream log shows a back arrow to the log and no "No dream". An entry opened from Today has `detailFrom: 'today'` (back, and a delete from the entry, return to Today). Journals home: back arrow and Android back to Today; Settings: back arrow and Android back to Today; Today: no arrow, Android back exits.
- **Resume on a new day** (`useToday`, `src/hooks/useToday.ts`): returns `{ todayKey, resumeNewDayToken }`. `todayKey` is the local date, refreshed on AppState `active` and by one timeout to the next local midnight plus 1 s (`msUntilNextDay`, built from date parts so DST days are right), cleared when the app leaves the foreground and on unmount; no polling. `resumeNewDayToken` starts at 0 and goes up by one each time the app returns to the foreground on a different day than it left on (several days away count once; a same-day return, a repeated `active` event and a foreground midnight never bump it). `App.tsx` reacts to the token only: if the launch is done and the data is loaded, no session is open, no delete is running, the screen is not capture, Read it back or Review, auto-open is on, and nothing is done today, it opens the launch Dream capture (from any other screen, Settings included). Each token is consumed once, so a resume that was blocked mid-flow does not try again that day. Today re-filters on a new day but never navigates by itself.
- **No dream marker** (`src/services/dayMarker.ts`, `src/hooks/useDayMarker.ts`): `Paths.document/no-dream.json` = `{"noDreamDate":"YYYY-MM-DD"}`, the latest skipped date only. It sits outside `dreams/` and the dream index, so saving, deleting and repairing dreams never touch it. Fail open: missing, zero-length, corrupt, wrong shape or a bad date reads as no marker (so capture opens). `markNoDream` updates state first and then writes; a failed write is swallowed (the value stays for the session); a slow read never overwrites a newer mark. **The app never deletes it**: a stale date is ignored and overwritten on the next skip. "Done today" is derived from the library and the marker, so deleting today's only finished dream re-opens capture on the next launch.
- **Settings** (`SettingsScreen`, `src/services/settingsStorage.ts`, `src/hooks/useSettings.ts`): header "Settings" with a back arrow ("Back to Today"), one `Switch` row "Open dream capture on launch" (default on) with the line "When off, the app opens to Today." `Paths.document/settings.json` = `{"autoOpenDreamCapture": true}`. Each key is validated on its own; missing, zero-length, corrupt, wrong shape or non-boolean falls back to on, so a damaged file never silences the prompt. Writes are read-modify-write, one at a time, keep unknown keys, swallow failures and never delete the file. The setter updates state at once; the toggle applies immediately and has no unsaved state. Off means launch always opens Today and resume changes nothing; "No dream" and "New dream" are unaffected.
- **Privacy**: the only new data is the latest skipped date and one boolean, in two small files on the device. Nothing leaves the phone.

11. **Icon and splash**: a moon mark. `assets/icon.png` (full-bleed), `android-icon-foreground/monochrome/background.png`, `favicon.png` and `splash-icon.png`; source SVGs and generation notes are in `assets/icon-source/`. The `expo-splash-screen` plugin in `app.json` shows the splash on #0D1017 at width 200. They need a native rebuild to appear (see Repo and workflow state).

**Data model** (`Dream`): `id`, optional `journalId` (absent means Dreams; see below), `createdAt` (ISO, when first stored; a draft counts), `durationMs` (0 when there is no audio), optional `audioFileName` (absent means no audio), `title` (empty only for drafts, old dreams and Life entries), optional `emotion`, `tags[]`, optional `transcript` (final edited text, trimmed, omitted when blank), optional `status: 'draft'` (absent means finished). Emotion is one optional string of lowercase emotions joined with ", ", shown as chips with a capital first letter; see the Review notes above. Older dreams may hold free text in other cases; it is split on commas and semicolons only (never spaces) and matched case-insensitively.

**Journals in the data**: one shared index holds every journal's records. A record's optional `journalId` (`'dreams'` or `'life'`) says where it lives; a record without one is a Dreams entry, so there is no migration and old data is untouched. Always read it through `journalOf(record)`, never `record.journalId`. A new save stamps the journal (`saveDream` takes `journalId`, on create only, and `requireTitle`, default true; Life passes false); an edit never changes it. An id this version does not know is kept in storage and hidden from both logs and from Search. Delete, safety copies and repair are journal-agnostic (by id). Known limit: an older app build opened on this data would show Life entries as dreams (downgrade); accepted.

**Storage layout**: everything is under `Paths.document`. Two small files sit beside the dream data and are not part of it: `no-dream.json` (the latest skipped date) and `settings.json` (the launch toggle); see item 10. The app never deletes either, and the dream save, delete and repair code never touches them. `dreams.json` is the index. `dreams.json.bak` is a best-effort copy of the previous index, made before a write only when the current index is non-empty (a failed copy does not block saving). `dreams.corrupt-<timestamp>.json` is a copy of an unparseable index, made at most once per app session. Audio is in `dreams/` as `<id>.m4a`, or `<id>-<k>.m4a` if that name was taken. Only the audio **file name** is stored, never a full path, because the document directory path can change between app updates on iOS; always resolve it through `audioFileName` / `dreamAudioUri`. Dreams saved before titles/tags existed load with `title: ''` and `tags: []`.

**Save order** (`saveDream`, an upsert by id; writes run one at a time): validate the title (only for a finished dream), copy the recording from the cache into `dreams/` (never overwriting), back up the index, write the index, and only then delete the cache file. If the index write fails, the copied audio is removed and the index is repaired from the in-memory pre-save list first, then from `.bak`; an intact index is never touched. A zero-length `dreams.json` counts as missing (a non-empty `.bak` is then the base). An unparseable non-empty index is never overwritten: saving throws `INDEX_UNREADABLE`, the list shows "Your saved dreams could not be read. Your recordings are safe.", and saving stays refused until a restore feature exists. On update, `undefined` for emotion or transcript keeps the stored value and `''` clears it.

**Delete order** (`deleteDream(id)`, a finished or any stored dream by id; serialized with saves; throws on any failure; "scrub first, commit last"): (1) read the index; an unparseable one throws `INDEX_UNREADABLE` and nothing is touched; an unknown id is a no-op. (2) Check the audio target before touching anything: a plain file name that resolves inside `dreams/` and is not referenced by another dream. (3) Classify the safety copies `dreams.corrupt-<digits>.json` (documents folder, files only) read-only: Tier 0 does not mention the dream and is left untouched; Tier 1 mentions it and holds only dreams that are in the live index (a pure duplicate) and is deleted; anything else (holds a dream missing from the live index, or cannot be read or validated) blocks the delete (`isSafetyCopyBlockedError`) with nothing changed. Copies are never rewritten. Classification uses a strict JSON-prefix validator that tolerates trailing NULs and a BOM. (4) Rewrite `dreams.json.bak` without the dream (`[]` if empty, never a zero-length file; if the rewrite fails the `.bak` is deleted; if both fail the delete aborts). (5) Delete the audio file just before the index write (a missing file counts as success). (6) Write the index without the dream: this write is the commit. If it fails, the index is repaired with the same helper `saveDream` uses (memory first, then `.bak`) and the error is rethrown; the dream stays listed. Everything before step 6 can be repeated safely, so a retry converges. The app never unlists a dream while its audio or safety copies remain.

**Recording flow detail**: the recorder writes to the cache directory. Nothing is stored permanently until Done or Finish later. Discarding (Read it back back arrow, after confirmation) deletes only the cache file of the new recording; files are deleted in only three cases: `saveDream`'s own rollback of the copy that same save just made (when the copy or the index write fails), `deleteDream` (see Delete order), and the cache file of a recording that was never saved. Nothing else.

## Decisions made during development

- **Stack**: Expo (SDK 57) + TypeScript, ESLint + Prettier, Jest. Local-only storage; no backend.
- **On-device only.** Transcription runs on the device; no audio or text is sent anywhere. In practice this means `expo-speech-recognition` with the on-device request; the airplane-mode check on Android passed.
- **A development build is required.** `expo-speech-recognition` has native code, so Expo Go cannot load the app (the whole bundle fails to load). `expo-dev-client`, `expo-asset` and `expo-splash-screen` are installed and `expo` is on `~57.0.27`.
- **Voice leads**, with "Write instead" as a secondary option. This resolved one open decision in `docs/product.md`.
- **Pause design**: recorder first, recognition stops while paused, a new session on resume, so the audio is always a superset of the transcript. A tap is ignored within 300 ms of the last one and after Save. Details are in `docs/spike-live-transcription.md`.
- **Flow**: Capture, Read it back, Review, Done. Nothing is stored permanently until Done or Finish later. Drafts are real dreams with `status: 'draft'`.
- **Emotion** stays free text entries the user creates with an input like the tag input (never a fixed list or rating); quick-pick chips come from words used before. Tag suggestions come only from tags used before. Nothing is derived from the content of a dream.
- **Storage safety**: copy-then-write-then-delete, a best-effort `.bak`, no overwrite of an unreadable index, one write at a time (decisions logged in the Steward repo).
- **System fonts for now.** The mockups use a display serif and a geometric sans; matching them would need bundled fonts.
- **Expo Router is NOT adopted.** `AGENTS.md` (from the Expo template) says to use it, but the app keeps the `App.tsx` state switch with `useDreamSession`. Do not add routes or another navigation library without asking.
- **"No dream"** is the label for dismissing capture (not "Skip"). **Title is required** to finish a dream; emotion and tags are optional.
- **Dream log and entry** (user, 2026-10-06): the log was not a journal home then (superseded by the multiple-journals decision below: the Journals home now sits above the logs). Search covers title, transcript, emotion and tags, local text matching only. The tag filter is multi-select and a dream must have all selected tags. Edit reopens Review; Done on an edited dream returns to its entry; "Finish later" is hidden for finished dreams. The draft sub-line is "Draft · <date>" with "Draft" in red and the date muted (changed from "Draft · Not reviewed yet · Finish now"). No delete in this work; "Also tagged" and "See all" were removed from the entry (to revisit with AI suggestions later; AI features remain out of scope for v1). System fonts kept.
- **OS floor** (user, 2026-10-06): older phones can install the app. Live text is off on Android below 33 and iOS below 17, with the quiet note "Live text isn't available on this phone."; there is no install-time block.
- **Type instead: keep the text, drop the audio.** Choosing "Type instead" while recording deletes the recording (after confirmation) and keeps the live text so far; the dream becomes a written dream with no audio.
- **Delete UX rework** (user, 2026-10-10): this supersedes the bottom red "Delete dream" button and the standalone Edit control on the entry. The entry has a top-right "..." menu with Edit and Delete. On the Dream log, swiping a finished row reveals Delete, and tapping it shows the same confirmation. In-flight behavior on the log is Notes-style (only the row being deleted is locked). Swipe uses `react-native-gesture-handler`'s legacy `Swipeable` (upstream-deprecated in favor of the Reanimated version; chosen to avoid adding Reanimated/worklets). Drafts stay non-deletable (superseded: drafts are now swipe-deletable too).
- **Delete for finished dreams** (user, 2026-10-10): permanent, no trash and no undo; a confirmation alert; drafts are deletable too since the journals validation fixes; safety copies never keep a deleted dream and never lose other dreams (a delete is blocked instead).
- **Multiple journals** (user, 2026-10-10): a journal is a container; the built-in ones are Dreams (existing dreams) and Life (the everyday entries); user-created journals come later. The Today page was built as Part 2 (see the next decision). No "Journals" link on dream capture: the Journals home is reached from a log's back arrow (now also from the book icon on Today). The Life header date line is "Life · <date>" (changed from date-only, user, same day); the Life title field is not autofocused. Cross-journal Search, the Life wording and the navigation above were approved. Wording changes come from the user's manual validation, not from questions to the user.
- **Today, Settings and the launch rule** (user, 2026-10-10): Today is the main hub and shows only today's entries from every journal. "Done today" means a finished Dream saved today or "No dream" chosen today (a draft does not count, Life entries do not); the app opens to Dream capture only when nothing is done and the toggle is on, else to Today. The skipped date is stored on the device (approved). A Settings page with one toggle, "Open dream capture on launch" (default on), reached from a gear on Today. The Journals home is reached from a book icon on Today (no "Journals" text link) and keeps a back arrow and Android back to Today; Android back on Today exits. Resume on a new day with nothing done jumps to Dream capture and honours the toggle. Dream capture from the Dream log has a back arrow and no "No dream". Wording was picked by the builders (copy in `TODAY_COPY`, the Settings strings); the user edits it during manual validation.
- **Audio is kept** alongside the transcript (except for written dreams, including those started with "Type instead"). The caption on the listening screen ("Audio and transcript are both kept") is now true.

The checklist is in `docs/spike-live-transcription.md`.
- The fading transcript look and readability on both platforms.
- "Type instead": the microphone is released afterwards, the cache file is deleted, the alert flow works on both platforms, and Read it back receives the text so far (focused, with the keyboard).
- Read it back and Review keyboard behavior, especially Android edge-to-edge (Read it back uses `KeyboardAvoidingView behavior="padding"` on both platforms; Review uses it on iOS only, with `behavior` undefined on Android, relying on window resizing there; the difference is unverified on a device).

- Android hardware back on Read it back and Review.
- The emotion input on Review: the keyboard and return key (`returnKeyType="done"`, `submitBehavior="submit"`: does Enter add the emotion and keep the keyboard open on both platforms?), the same for the tag input,, and that a comma or semicolon from the soft keyboard or an IME creates the emotion.

**Accepted gaps**

- Type instead: if `recorder.stop()` fails after live text has stopped, the alert shows and the user stays on the Listening screen with live text stopped (the recording continues; nothing is deleted). Not handled.
- A native `stop()` that throws during pause is not handled. A resume after a fatal recognition error, before its `end` arrives, can leave live text off for the rest of that pause cycle (recording is unaffected). There is no visible state while a resume is in flight.
- Storage: the index write is not atomic. A kill mid-write can leave an empty or partial index; if every repair step also fails, the whole index can be lost. `.bak` is copied non-atomically and is not strictly the last known good. **A restore-from-backup feature is not built and needs the user's approval.**
- On Read it back the recording card is unmounted while the keyboard is visible, so playback stops and its position resets when the keyboard opens (user decision: keep stop-and-reset).
- Review card accessibility label includes the whole first line of the transcript, so a very long first line is read in full (cap or leave: undecided). The Review card and the Dream log row accessibility labels read long dates.
- Delete (finished dreams) known gaps:
  - After a crash or an index-write failure right after the audio is deleted, the dream stays listed with a missing (silent) recording; text is intact and a retry finishes the delete.
  - A safety copy holding only a fragment of the deleted dream, cut before its id or audio name, is not detected and stays (read-only detection limit). Multi-point damage that leaves a copy valid JSON cannot be detected either.
  - A delete is blocked when a safety copy cannot be proven safe, and there is no in-app way to resolve it yet (needs the future restore-from-backup).
  - There is no missing-audio state in the player.
  - OS-level device backups and orphan audio from failed saves are out of scope.
- A brand-new dream with nothing to keep is not saved by Finish later, so an empty draft can only arise by clearing a reopened draft's contents and leaving. No restore-from-backup. No "Also tagged" or "See all" on the Dream entry (to revisit with AI suggestions later).
- Live text is Android 13+ and iOS 17+ only; below that the app records audio only and shows a quiet note ("Live text isn't available on this phone."). The wording is the working text (not formally approved; the user will send small copy tweaks from their own testing); the floor itself is decided (see Decisions: older phones can install).

- Journals, known limits: Pre-existing risk: back while recording on Dreams capture can orphan the recorder's cache file (`useDreamRecorder` has no unmount cleanup); Life capture avoids it because its back is inert while recording.
- Journals, not yet verified on a device (covered only by typecheck, lint and Jest; iOS untested for all of it): the Android back chain across every screen; the Journals home layout; Life voice capture end to end (permission, live text, save, Read it back, Review without a title); upgrade-in-place over an existing install with real dreams, drafts and audio; swipe-delete in the Life log; how cross-journal Search feels (keyboard, chips).

## Gotchas

- Run `npm run check` (typecheck, lint, format check, tests) before calling anything done.
- In tests, native modules must be mocked. `expo-audio` is mocked per test file; `expo-file-system` uses `src/test/fakeFileSystem.ts` via `jest.mock('expo-file-system', () => jest.requireActual('../test/fakeFileSystem'))`. With React Native Testing Library v14, `render` and `fireEvent` are async: `await` them.
- Storage changes need careful tests with the faithful fake `src/test/fakeFileSystem.ts` (it models async copy/move, no-overwrite and failure injection).
- Use `SafeAreaView` from `react-native-safe-area-context`, not from `react-native` (deprecated). The app is wrapped in `SafeAreaProvider` in `App.tsx`.
- Install packages with `npx expo install`, and check Expo's versioned docs before touching Expo APIs (see `AGENTS.md`); Expo APIs change between SDKs.
- On Windows, the PowerShell tool sometimes reports exit code 255 for commands that actually succeeded (seen with some git and npm commands). Read the output to confirm.
