# Lucid

Voice-first notes app. Notes are markdown, organized by `#tags`, with voice notes attached. Read `docs/product.md` before building features, UI or copy. If a request conflicts with it, raise it instead of guessing. Read `docs/status.md` to see what is built, what is stubbed, known gaps and gotchas, and keep it current when you change the state of the project.

@AGENTS.md

## Stack

- React Native with Expo (SDK 57), TypeScript. A development build is required (`expo-speech-recognition` has native code); see `docs/ios-dev-build.md`.
- ESLint (`eslint-config-expo`) and Prettier

## Commands

```bash
npm start           # Metro dev server; open the installed development build (Expo Go cannot load this app)
npm run check       # typecheck + lint + format check + tests
npm test            # Jest only (jest-expo preset, Testing Library)
npm run test:watch  # Jest in watch mode
npm run format      # apply Prettier
```

Also `src/components/{EmotionInput,DreamChips,OverflowMenu,EntryRow,SwipeEntryRow,SwipeActionRow,NewJournalSheet,SearchIcon,TodayIcons,TodayEntryRow,AddEntryMenu,OutlinedChips,MicIcon,RecordingPlayer,JournalPicker,EntryToolbar,RecordingPanel,VoiceAttachmentCard,TaggedBodyInput,TaggedText,TagSuggestionBar}.tsx`, `src/screens/{AddEntryScreen,AddEntryWithVoice,JournalsScreen,SearchScreen,TodayScreen,SettingsScreen}.tsx` (the add-entry page is `AddEntryWithVoice` wrapping `AddEntryScreen`), `src/hooks/{useEntrySession,useEntryHistory,useKeyboardInset,useRecordingPlayback,useDreamLibrary,useJournals,useLogView,useToday,useDayMarker,useSettings,useDreamRecorder}.ts`, `src/services/{dayMarker,settingsStorage,journalStorage}.ts` (beside `dreamStorage.ts`), `src/utils/{emotions,capitalizeFirst,sessionNavigation,dreamLog,paragraphs,confirmDelete,journals,journalName,journalSearch,today,format,tags,inlineTags,tagSuggestions,waveform}.ts` (`inlineTags` is the pure scanner for inline `#tags`; `tagSuggestions` ranks tags for the suggestion bar), `src/types/entry.ts`, `StoredRecording` / `recordingsOf` in `src/types/dream.ts`, `src/test/fakeKeyboard.ts` (test helper that drives the mocked `Keyboard` events), `src/test/bodyText.ts` (reads the add-entry body input's text), and `jest.setup.ts` at the root. See the file map in `docs/status.md`.
- Navigation is React Navigation's native stack (`src/navigation/RootNavigator.tsx`): `Today` is the root, and `Log`, `Settings`, `Search` and `Add` are pushed over it (`routes.tsx`, `AddRoute.tsx`); there is no screen state switch in `App.tsx`. The journals drawer is the `JournalsDrawer` component rendered by Today, not a navigator. Flow state lives in `src/app/AppFlowProvider.tsx`: the launch rule (`launchPage`), the stored dreams (`useDreamLibrary`), the log's filter, search and scroll (`useLogView`, one for the logs and one for Search), the in-progress entry (`src/hooks/useEntrySession.ts`, origins `new | draft | edit`; an edit keeps a baseline) and `backFromAdd`, which decides leaving the `Add` route; `usePreventRemove` in `AddRoute.tsx` sends every prevented back there. The `Add` route is the single add-entry page: it creates new entries, reopens drafts and edits finished entries. `AGENTS.md` calls for Expo Router (`src/app/`); it is not adopted (the navigation library is React Navigation), so do not add routes or another navigation library without asking.

## Working rules

- Run `npm run check` before calling any task done, and report failures instead of hiding them.
- Tests are Jest files next to the code (`*.test.ts` / `*.test.tsx`). Add or update tests with behavior changes. Native modules are mocked in tests; `src/test/fakeFileSystem.ts` is a faithful in-memory `expo-file-system` (async copy/move, no overwrite, failure injection); storage changes need careful tests with it.
- Add dependencies with `npx expo install <package>`, and prefer Expo modules over third-party libraries.
- Use the vocabulary in `docs/product.md` (Note, Title, Tag, Body, Voice note, Transcript, Today view, Todo view, Untagged view, Pinned, Recently Deleted, Drawer, Search) in UI copy, code and data models. New code does not use Journal, Entry, Dream, Life, Emotion or Draft; those are retired (see "Retired terms and migration" in `docs/product.md`) and survive only in the old code until it is removed (chunk 8) and in the migration reader.
- Use `SafeAreaView` from `react-native-safe-area-context`, not `react-native`.
- UI copy is plain language. No psychological or Jungian terms, no interpretation of notes, no streaks, scores or gamification.
- Do not build anything under "Not in scope yet" in `docs/product.md` (AI features, tasks as a feature, nested tags, markdown beyond headings, lists, checkboxes, bold and italic, automatic purge of Recently Deleted, threads, roundups, explore view, desktop) unless asked. The Todo view only lists notes that contain plain-markdown checkboxes; do not add due dates, reminders or completion tracking.
- A note's title, preview, tags and Todo flag are derived from its body by pure functions in `src/utils/`; they are never stored. Read tags only through `inlineTags` (never hand-roll a `#` regex). Do not store a title or tags field on a note.
- Device access and persistence live behind hooks and services (`useDreamRecorder`, `useNoteSession`, `services/notesStorage.ts`, and until removed `useEntrySession`, `services/dreamStorage.ts`), not in screens. Notes and dreams are stored locally; transcription is on-device only (no audio or text leaves the phone). Storage layout and save order are in the storage section of `docs/status.md`. Safety rules:
  - Notes (new concept; the older list below governs the old dream code until chunk 8 removes it). The only app-initiated paths that delete files of notes data are: (1) Delete forever, for the one note the user chose to delete from Recently Deleted: every audio file that note lists inside `notes/`, each only if its stored file name is a plain name, resolves inside `notes/`, and no recording of any other note references it, then the index entry (index written last, so a note is never unlisted while its audio remains); (2) Empty Recently Deleted, which is only a loop of case (1) over the notes that have `deletedAt`; (3) the rollback of a failed save, which deletes only the file copies that same save just made (nothing previously stored); (4) discarding a recording that was never saved, which deletes only its cache file. Cases (3) and (4) apply only to files the app created and never stored. Nothing else. Moving a note to Recently Deleted (soft delete) sets `deletedAt` in the index and never deletes a file; Restore clears `deletedAt`. There is no automatic purge, ever; adding one needs an explicit user decision and a change to this list. Handling of safety copies (`.bak`, `corrupt-<ts>`) in Delete forever is TBD (architect, chunk 3). Whether closing a stored voice note deletes its audio is undecided (Open in `docs/product.md`); until decided, no notes code deletes a stored recording on close.
  - Notes live in `notes.json` (index, written atomically via a temp file; `notes.json.bak` recovery copy; an unreadable index means refuse to write, and the damaged file is kept as `notes.corrupt-<ts>.json`), with voice note audio in `notes/`. All writes go through `services/notesStorage.ts`.
  - `dreams.json`, `dreams/` and their safety copies are read-only legacy data. Nothing may modify or delete them except the migration reader, and the migration reader only reads them (it never writes to or removes them). The import marker (`migrated.json`) is the only file the migration writes besides `notes.json` and `notes/`.
  - The day marker file (the date the user last finished or skipped the launch note) and `settings.json` live beside the notes index and are never deleted (only overwritten). The marker file keeps the name `no-dream.json` for now; whether it is renamed is TBD (architect, chunk 3).
  - The app deletes files only in these cases: (1) `saveDream`'s own rollback of the copies that same save just made (each new recording it copied into `dreams/`; the source cache files are never deleted before the index has been written); (2) `deleteDream`, for the one dream the user chose to delete: every audio file that dream lists (each recording from `recordingsOf`, including the legacy single `audioFileName`) inside `dreams/`, each only if its stored file name is a plain name, resolves inside `dreams/`, and no recording of any other dream references it (`deletableAudioFiles`), `dreams.json.bak`'s copy of it, and any `dreams.corrupt-<digits>.json` safety copy that holds only dreams already in the live index (a copy that holds anything unaccounted for blocks the delete; copies are never rewritten); (3) the cache files of recordings that were never saved (one per unsaved recording, including when the user discards a recording to leave the add-entry page, and the cache files of recordings that were closed or replaced before saving); (4) deleting a custom journal, which is only a loop of case (2); (5) `saveDream` with `removeRecordings` (or `removeAudio`, meaning all of the entry's stored recordings), for the one entry the user chose to remove one or more recordings from (the entry itself is kept): only the audio files of the recordings named for removal, which must belong to that entry (an unknown name throws and deletes nothing), each only if its stored file name is a plain name, resolves inside `dreams/`, and no recording of any other entry, nor of a recording this entry keeps, references it; each deleted only after the index has been written without it, then `dreams.json.bak` is rewritten from the new index so it no longer names the files. Safety copies (`dreams.corrupt-<digits>.json`) are never touched by this case. Nothing else. `deleteDream` writes the index last, so a dream is never unlisted while its audio or safety copies remain.
  - Deleting a custom journal is allowed (custom only: Dreams and Life are never deletable, guarded by `isBuiltInJournal`), and only after a modal confirm that shows the entry count. It removes all of the journal's entries, drafts included, with their audio, through the existing per-entry `deleteDream` path (`useDreamLibrary.removeMany`: sequential, stops at the first failure). The registry definition is removed last, after re-reading storage. Irreversible. `journals.json` is never deleted (replaced atomically; a damaged copy is kept as `journals.corrupt-<n>.json`).
  - Journals are runtime data: the registry comes from `useJournals` / `services/journalStorage.ts` (`journals.json`, beside the dream index; atomic write via a temp file, temp-file recovery, safety copy of damaged content) and is passed explicitly to screens and utils, not read from a global. `BUILT_IN_JOURNALS` are the only constants. Names (`utils/journalName.ts`) are 1-24 characters and unique case-insensitively, including Dreams and Life. `journalCopy` is keyed by the journal object (built-ins use their kind's copy, custom journals use their name), not by id or kind.
  - Downgrade: a build from before journals ignores `journalId` and shows custom-journal and Life entries as dreams; a build that knows only Dreams and Life hides custom-journal entries. Data is kept either way (see `docs/status.md`).
  - A stored entry holds its voice recordings in the additive `recordings` list (`{ fileName, durationMs, waveform? }`), which is the truth when present; there is no cap on recordings per entry. `saveDream` also mirrors the FIRST recording into the legacy `audioFileName` / `durationMs` / `waveform` fields (and removes those fields when the list is empty) so older builds still read one recording. Only `saveDream` writes the mirror; other code never reads the legacy fields directly, only through `recordingsOf`, which falls back to them for entries that have no `recordings`. A legacy entry is converted lazily, the first time it gains or loses a recording.
  - Downgrade (recordings): a build from before multiple recordings shows and plays only the first recording of an entry, and if it deletes that entry it removes only that first file, leaving the other recording files in `dreams/` unreferenced (orphans). It keeps the `recordings` field when it edits an entry, but cannot keep the mirror in step if audio changed, so it never changes audio. Data is kept either way.
  - `no-dream.json` (the No dream date) and `settings.json` live beside, not inside, `dreams/` and the dream index, and are never deleted (only overwritten). They fail open: a missing or unreadable file means not done / defaults, and a failed write never reaches the UI.
  - Read a record's journal only via `journalOf` (legacy records have no `journalId`); never read `record.journalId` directly.
  - Resolve audio through `recordingsOf(dream)` (the stored recordings, or the legacy single one) and `recordingUri(recording)` / `dreamAudioUri(dream)` (the first recording's URI); delete only through `deletableAudioFiles`. Never read `dream.audioFileName` directly and never build `<id>.m4a`.
  - When updating a dream always pass full `details` (emotion and transcript strings): `undefined` keeps the stored value, `''` clears it.
  - A zero-length `dreams.json` counts as missing, so `deleteDream` writes `[]` when the last dream goes, never an empty file.
- The rules below about Save draft, Discard, Keep writing, the check, `removeRecordings` on an explicit save, journals and `no-dream.json` describe the older code that still exists and stay until chunk 8 removes it. The notes concept has no Draft, no check and no leave prompts: the editor autosaves (Planned in `docs/product.md`). Do not copy those rules into notes code.
- `backTarget` in `src/utils/sessionNavigation.ts` is the single source of back behaviour (on-screen arrows and Android hardware back alike); `performBack` in `App.tsx` carries it out. For the `add` screen it returns `chain` and `backFromAdd` in `App.tsx` decides: a running recording always asks to discard first (`entryLeaveRef`, created in `App.tsx` and handed to `RecordingPanel`; discarding deletes only the unsaved cache file, never anything in `dreams/`, then carries on leaving); an edit asks "Discard changes?" only when it changed; a new entry or draft with anything on it (including a stored recording that was closed) asks Save draft / Discard / Keep writing; an EMPTY new page just closes. Backing out of an empty launch page (the Dreams page opened by the launch rule, auto-open setting or new-day resume: `launchPage` in `App.tsx`) counts as No dream (marker written, goes to Today); with content it uses the leave prompt and is not No dream. Android back on the launch page therefore goes to Today; only Today exits the app.
- Back is blocked while a save is in flight (an edit's save too), and the add-entry page's fields, toolbar, check and back are locked then. It is also blocked while a delete started from the Dream entry is in flight (Edit is ignored too). While a journal delete is in flight (`deletingJournalId` in `App.tsx`), its entries and the journal itself are hidden and any screen showing it returns to Journals home; the Rename sheet (`renamingJournalId`) belongs to Journals home and closes when leaving it or when its journal is gone or being deleted; a delete started from the Dream log does not block back or navigate.
- The add-entry page (`AddEntryWithVoice`): the voice recordings are attachments of the entry session, a LIST (`recordings`: each `{ id, uri, fileName?, persisted, removed, durationMs, waveform? }`), shown as stacked cards above the title, each with its own play, waveform, duration and close. The mic stays available after a recording, so another can be added (no cap); one card plays at a time. Closing a card only sets that recording's `removed` (reversible by undo; nothing is deleted or forgotten); a new recording's cache file is deleted only after a successful save or when the page is left, including cache files of closed or replaced recordings; a STORED recording is removed only by `saveDream` with `removeRecordings` (deletion case 5), triggered by an explicit save (the check, or Save draft on the leave prompt) after the user closed it. Undo/redo (`useEntryHistory`) covers body text (tags are `#tag` words in the body, so typing them is covered) and closing or restoring a card (each history step names its recording), never the title or journal. The journal is switchable only for a new entry that was never saved (`entryJournalLocked`). Emotion is not on the page; an edit must pass the stored emotion back unchanged. `waveform` is an optional additive field of each stored recording (and of the legacy mirror); read it only through `sanitizeWaveform` / `isValidWaveform`.
- Tags live in the body as `#tag` words; the page has no tag row and no `TagInput`. `inlineTags(body)` (lowercase, de-duplicated, in order of first appearance) is the ONLY source of an entry's stored `tags` on save, and the body is stored unchanged as `transcript`. Read and write tags only through `src/utils/inlineTags.ts` (`scanTags`, `inlineTags`, `activeToken`, `completeToken`, `insertHash`, `materializeTags`, `missingInlineTags`); never hand-roll a `#` regex, and never call `saveDream` with tags that did not come from `inlineTags(body)`. Opening a stored entry appends its stored tags that the body lacks as a trailing `#tag` line (`entrySessionFromDream` / `materializeTags`, whitespace and terminator characters in an old tag become `-`); that addition is seeded as one undo step (`materializedFrom`) and is part of the edit baseline, so merely opening an entry is not an edit. Because the stored `tags` come only from the body, an old stored tag that cannot be an inline token (empty after sanitising, only digits, or over 40 characters) is not added to the body and is dropped from the stored tags on the next save, and odd tags are respelled with `-` ("bad dream" becomes `#bad-dream`) on that save. The Dream entry highlights the same words with `TaggedText` and shows tags it holds that the text lacks as a `#tag` line after the text; the entry no longer shows tag chips (log rows, Today and Search still show tag chips from the stored `tags`).
- The add-entry page's bottom dock (`entry-bottom-dock`: suggestion bar above the toolbar) is lifted above the keyboard by `AddEntryScreen`: on iOS `KeyboardAvoidingView` (`behavior="padding"`) does it; on Android, where edge-to-edge means the window does not resize, `useKeyboardInset` (the keyboard's visibility and height, from the `Did` events on Android and the `Will` events on iOS) gives the dock a bottom padding of keyboard height plus the bottom safe-area inset (the bottom inset alone when the keyboard is closed). Do not add `KeyboardAvoidingView` behaviour on Android or measure the keyboard elsewhere. Tests drive the keyboard with `src/test/fakeKeyboard.ts`.
- The add-entry body is a `TaggedBodyInput`: a multiline TextInput with NO `value` prop whose children are the text split into plain and `#tag` runs (tags styled with the accent colour). RN forbids `value` with children, so typing is mirrored into state (never remounts) and a programmatic change (undo, redo, the # button, a tag suggestion) REMOUNTS the input, restores the cursor via `selection` and refocuses. Tests read its text with `bodyText()`, not `props.value`. The tag suggestion bar (`TagSuggestionBar`, in the bottom dock above the toolbar) shows only while the body has focus and the cursor is in a `#word`, and completes it as one undo step (the "#" button is `insertHash`, also one step). Its tags are the stored ones (`tagsByUse(library.dreams)` in `App.tsx`, passed as `knownTags`) plus the tags already typed elsewhere in the entry, ranked by `suggestTags` (prefix, then substring; at most 8).
- On the Dream entry, Edit and Delete live in the top-right "..." menu (`OverflowMenu`, an in-screen overlay, not a `Modal`). On Android, hardware back closes the open menu first, before the screen's back.
- `App.tsx` is wrapped in `GestureHandlerRootView` (swipe-to-delete uses `react-native-gesture-handler`'s `Swipeable`, wrapped in the shared `SwipeEntryRow` used by the logs and Today, and `SwipeActionRow` for the Journals home rows). Jest needs `jest.setup.ts` (listed in `package.json` `jest.setupFiles`), which imports `react-native-gesture-handler/jestSetup`.
- Editing a finished dream never calls `save('draft')` and never discards its persisted audio, except through `removeRecordings` (or `removeAudio`) for recordings the user closed, applied only when they explicitly save (the check, or Save draft on the leave prompt).
- Keep changes small. The default branch is `main`. All work happens on a feature branch; never commit directly to `main`. Feature branches may be pushed to `origin`; changes reach `main` only through a pull request from a feature branch, which the user reviews and merges. Never push to `main`, never merge a PR yourself, never force-push, and never delete remote branches.
- Never create or edit `ios/` or `android/` by hand; configure native behavior in `app.json`.
